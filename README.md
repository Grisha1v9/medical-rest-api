# Medical REST API (with LangGraph)

REST API для медицинского приложения: принимает показатели пациента (возраст,
давление, пульс, температура, жалобы), валидирует их, прогоняет через агентный
пайплайн **LangGraph** для оценки уровня риска (LOW / MEDIUM / HIGH), формирует
рекомендацию и сохраняет результат в SQL-базу **SQLite**.

```
JSON-запрос → FastAPI → валидация Pydantic → LangGraph (analyze → recommend) → SQLite → JSON-ответ
```

> Обработка данных — демонстрационная rule-based логика: акцент проекта на
> структуре API, валидации и документировании, а не на сложности модели.

## Что реализовано (по пунктам задания)

| # | Требование | Реализация |
|---|---|---|
| 1 | REST API на FastAPI, ≥4 эндпоинтов | **5 эндпоинтов**: POST /predict, GET /results, GET /results/{id}, DELETE /results/{id}, GET /health |
| 2 | Pydantic-модели с типами, обязательностью, ограничениями | 3 модели; ограничения диапазонов через `Field(ge/le)`, необязательное поле `Optional`, кросс-полевая валидация через `model_validator` |
| 3 | POST-эндпоинт с обработкой данных → JSON | POST /predict: данные проходят граф LangGraph, ответ — структурированный JSON с уровнем риска и рекомендацией |
| 4 | Список объектов + запись по ID, разные HTTP-методы | GET /results (пагинация skip/limit), GET /results/{id}; методы **GET, POST, DELETE** |
| 5 | Обработка ошибок | 404 (несуществующая запись), 422 (выход за диапазон, отсутствующие поля, неверный тип параметра, нарушение связи полей) |
| 6 | Дополнительный сценарий | **SQL-база данных**: SQLite + SQLAlchemy, полный CRUD, таблицы создаются при старте (lifespan) |
| 7 | Swagger UI | Все маршруты в автодокументации `/docs` с описанием, параметрами и схемами ответов; проверены корректные и ошибочные запросы |
| 8 | Локальный запуск | Код разделён на 5 логических модулей, `requirements.txt`, инструкция ниже |

## Реализация

### Эндпоинты

| Метод | Путь | Назначение | Успех | Ошибки |
|---|---|---|---|---|
| POST | `/predict` | Приём данных пациента, обработка через LangGraph, сохранение в БД | 200 | 422 |
| GET | `/results` | Список результатов, пагинация `?skip=0&limit=10` | 200 | 422 |
| GET | `/results/{id}` | Получение записи по идентификатору (path-параметр) | 200 | 404, 422 |
| DELETE | `/results/{id}` | Удаление записи по идентификатору | 200 | 404 |
| GET | `/health` | Служебная информация о приложении | 200 | — |

### Pydantic-модели (`schemas.py`)

- **PatientInput** — входные данные: возраст, систолическое/диастолическое
  давление, пульс, температура (обязательные, с ограничениями диапазонов),
  жалобы (необязательное поле `Optional[str]`).
- **PredictionResult** — ответ API: id, данные пациента, уровень риска,
  рекомендация, время создания. Используется как `response_model`, поэтому
  FastAPI автоматически строит схему ответа в OpenAPI.
- **HealthInfo** — служебная информация: имя приложения, версия, число эндпоинтов.

Ключевая особенность — кросс-полевая валидация давления:

```python
@model_validator(mode="after")
def check_bp(self):
    if self.diastolic_bp >= self.systolic_bp:
        raise ValueError("diastolic_bp must be less than systolic_bp")
    return self
```

Каждое поле по отдельности может проходить ограничения диапазонов, но
диастолическое давление не может быть выше систолического — эту связь ловит
именно `model_validator`, возвращая 422 с понятным сообщением.

### Обработка данных через LangGraph (`langgraph_agent.py`)

Граф из двух узлов над общим состоянием (`AgentState`, TypedDict):

```
START → analyze → recommend → END
```

- **analyze** — считает баллы риска по правилам:

  | Условие | Баллы |
  |---|---|
  | возраст > 60 | +1 |
  | систолическое > 140 или диастолическое > 90 | +2 |
  | пульс > 100 или < 60 | +1 |
  | температура > 37.5 | +1 |

  Итог: **≥3 баллов → HIGH**, **2 → MEDIUM**, **≤1 → LOW**.

- **recommend** — формирует текстовую рекомендацию по уровню риска
  (плановый осмотр / консультация терапевта / срочная госпитализация).

### SQL-сценарий (`database.py`, `crud.py`)

- База SQLite (`medical.db`), таблица `results` описана ORM-моделью
  `ResultRecord`: входные показатели, уровень риска, рекомендация, время
  создания (timezone-aware).
- Таблицы создаются при старте приложения через механизм **lifespan**.
- Сессии БД выдаются через зависимость `Depends(get_db)` и закрываются
  после каждого запроса.
- Полный CRUD: сохранение (POST), список с пагинацией (GET), чтение по ID
  (GET), удаление (DELETE). Данные сохраняются между перезапусками сервера.

### Обработка ошибок

| Ситуация | Код | Пример ответа |
|---|---|---|
| Запрос несуществующей записи (`/results/9999`) | 404 | `{"detail": "Result 9999 not found"}` |
| Значение вне диапазона (`age=150`) | 422 | `less_than_equal`, поле `body.age` |
| Отсутствуют обязательные поля | 422 | `missing` для каждого поля |
| Неверный тип path-параметра (`/results/abc`) | 422 | `int_parsing` |
| Диастолическое ≥ систолического | 422 | `value_error` — собственный валидатор |

## Запуск

### Требования

- Python **3.11+**
- Зависимости из `requirements.txt`

### Шаг 1. Перейти в папку проекта

```bash
cd med_api/app
```

### Шаг 2. Создать виртуальное окружение

```bash
python -m venv .venv
```

### Шаг 3. Активировать окружение

| Оболочка | Команда |
|---|---|
| **Windows / Git Bash (MINGW64)** | `source .venv/Scripts/activate` |
| Windows / PowerShell | `.venv\Scripts\Activate.ps1` |
| Windows / CMD | `.venv\Scripts\activate.bat` |
| Linux / macOS | `source .venv/bin/activate` |

После активации в начале строки терминала появится `(.venv)`.

### Шаг 4. Установить зависимости

```bash
pip install -r requirements.txt
```

### Шаг 5. Запустить сервер

```bash
uvicorn main:app --reload
```

Признаки успешного запуска:

```
INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)
INFO:     Application startup complete.
```

Остановка: `Ctrl+C`. Если порт 8000 занят: `uvicorn main:app --reload --port 8001`.

### Куда перейти в браузере

| Адрес | Что откроется |
|---|---|
| **http://127.0.0.1:8000/docs** | Swagger UI — главная точка входа, здесь выполняются все запросы |
| http://127.0.0.1:8000/redoc | ReDoc — альтернативная документация |
| http://127.0.0.1:8000/openapi.json | OpenAPI-спецификация |
| http://127.0.0.1:8000/health | Служебная информация (открывается прямо в браузере) |
| http://127.0.0.1:8000/results | Список результатов (открывается прямо в браузере) |

> Корневой адрес `/` вернёт 404 — отдельного маршрута для него нет, начинайте с **/docs**.

### Как выполнить запрос в Swagger UI

1. Открыть **/docs** → развернуть эндпоинт → **Try it out**
2. Вставить JSON в **Request body** → **Execute**
3. Ниже появятся реальный ответ, код статуса и curl-команда

### Примеры запросов (POST /predict)

Стабильный пациент → **LOW**:

```json
{
  "age": 30,
  "systolic_bp": 120,
  "diastolic_bp": 80,
  "heart_rate": 70,
  "temperature": 36.6,
  "symptoms": "нет жалоб"
}
```

Пациент высокого риска → **HIGH**:

```json
{
  "age": 72,
  "systolic_bp": 170,
  "diastolic_bp": 100,
  "heart_rate": 118,
  "temperature": 38.4,
  "symptoms": "одышка, слабость"
}
```

Ошибка валидации → **422** (диастолическое выше систолического):

```json
{
  "age": 40,
  "systolic_bp": 100,
  "diastolic_bp": 120,
  "heart_rate": 72,
  "temperature": 36.6
}
```

### Проверка базы данных

```bash
python check_db.py
```

Выведет схему таблицы `results` и все сохранённые записи — подтверждение,
что данные действительно хранятся в SQLite.
